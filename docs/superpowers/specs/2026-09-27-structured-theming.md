# HelixIAM: replace free-form realm CSS with a safe, structured theming system

You are working in the HelixIAM repository (github.com/melmarzgioui/helixiam): a Java 21 / Spring Boot
OAuth2 / OIDC / SAML identity provider with server-rendered Thymeleaf pages, PostgreSQL (Flyway), an
admin REST API, and realm import/export. Target the next minor version after 1.0.

## Why

Realms are themed today through `customCss`, a free-form CSS string stored in the database
(`realm_config.custom_css`) and inserted into pages raw with `th:utext`. That has four problems.

1. **Security.** Anyone with realm-admin rights, or a stolen admin token, can:
   - add `</style><script>…</script>` and run script on the sign-in page, which is enough to
     phish passwords and one-time codes;
   - leak typed input with CSS alone: attribute selectors plus `background-image: url(https://attacker/…)`
     work, because the CSP allows `img-src https:`;
   - keep all of this working only because the CSP needs `style-src 'unsafe-inline'`.
2. **Fragility.** Realm CSS has to target internal class names (`.helix-form`, `.brand-mid`, …). Any
   template change silently breaks every customer's branding.
3. **Coverage.** Only `login.html` and `register/register.html` insert it. Every other user-facing
   page shows the default look halfway through sign-in, including two-step enrolment and entry,
   recovery codes, reset, consent, required actions, magic link, the flow pages and the account console.
4. **Operations.** The CSS isn't cacheable, isn't in version control, and has no preview or validation.

## Goal

A realm, and optionally an organization within it, can be themed completely without writing CSS.
It works through validated, structured settings that HelixIAM renders itself, applied to every
user-facing page and email. Free CSS stays only as a tightly restricted escape hatch. Operators who
want themes in version control can mount them as files.

## Design

### 1. Theme model (realm level, with an optional organization override)

Add a `theme` object, stored as structured columns or validated JSON, never as raw CSS.

**Colours** (each `#RRGGBB`, with `light` and `dark` variants):
- `primary`, `primaryStrong`, `primaryTint`
- `surface`, `surfaceRaised`, `surfaceSunken`
- `ink`, `inkMuted`, `border`
- `negative`, `negativeTint`, `positive`, `positiveTint`, `focusRing`

**Typography:**
- `fontSans` and `fontDisplay`. Each is either a built-in stack name (system-sans, system-serif,
  system-mono) or the name of a font uploaded to the realm (see 3).
- `baseSize` (14–18 px)

**Shape:**
- `radius` (0–16 px)
- `density` (`comfortable` or `compact`)

**Assets:**
- `logoUrl` and `logoDarkUrl`: https only, or an uploaded asset
- `faviconUrl`
- `brandImageUrl` (optional side-panel image)

**Layout:**
- `layout`: `split` (brand panel and form) or `centered` (form only)
- `showLanguageSwitcher` (bool)
- `supportedLocales` (a list; one entry hides the switcher)

**Texts** (plain text, escaped, localised per locale with a fallback to the built-in messages):
- `brandHeadline`, `brandSubhead`, `brandByline`
- `welcomeText`, `footerText`
- `brandBadges` (list; empty hides them)
- links: `privacyUrl`, `termsUrl`, `supportUrl` (https only)

**Contrast:** `dark` variants are optional, and HelixIAM derives defaults from the light values.
Validate WCAG AA contrast for ink on surface and for text on primary, and return a clear error or
warning that names the failing pair.

**Precedence:** organization theme (when an organization is in context) → realm theme → HelixIAM
default. Merge field by field.

### 2. Rendering

- A single shared head fragment used by **every** user-facing template:
  - login, register and register-success
  - mfa (enable, totp, recovery-codes, webauthn-register)
  - reset (all), consent, activate
  - required-actions, magic, flow, maintenance
  - me/account console
- The fragment:
  - links the base stylesheet;
  - links `/realms/{r}/theme.css` (plus `?org={id}` when an organization is in context);
  - sets the favicon, `<meta name="theme-color">`, and the logo and texts from the model.
- `/realms/{r}/theme.css` is generated by HelixIAM from the model:
  - It contains only CSS custom properties (`--hx-primary`, `--hx-surface`, `--hx-font-sans`,
    `--hx-radius`, …), with light values in `:root` and dark values in a
    `@media (prefers-color-scheme: dark)` block.
  - It is served with `Content-Type: text/css`, a strong ETag and `Cache-Control: public, max-age=300`,
    and it changes when the theme changes.
- Refactor the base stylesheets so every colour, font, radius and spacing value comes from those
  variables. This set of variables becomes the **documented, versioned theming contract**: list them in
  `docs/THEMING.md` with their meaning, and keep them stable across minor versions.
- Emails (verification, reset, magic link, OTP) use the same logo, colours, texts and footer through the
  email templates.

### 3. Fonts and assets

- Realm assets are uploaded through the admin API, stored in the database (or object storage behind an
  interface) and served from HelixIAM's own origin at `/realms/{r}/theme/assets/{id}.{ext}`:
  - fonts: `woff2` only, at most 500 KB each and 8 per realm;
  - images: `svg` (sanitised: no scripts, no external references, no `foreignObject`), `png` or `webp`,
    each with a size limit;
  - responses carry the correct `Content-Type`, `X-Content-Type-Options: nosniff`, and a
    `Content-Disposition` that suits the type.
- The theme's font fields refer to uploaded fonts by name. The generated `theme.css` emits
  `@font-face` rules for them. `font-src` stays `'self'`.

### 4. Escape hatch: restricted custom CSS

Keep `customCss`, but:
- serve it inside `/realms/{r}/theme.css` (after the variables), never inline;
- cap it at 32 KB;
- reject anything that isn't plain CSS, with a clear error naming the offending construct:
  - `<` (so no `</style>` breakout)
  - `@import`, `@charset`, `@namespace`
  - `expression(`, `behavior:`, `-moz-binding`, `javascript:`
  - `url(` whose target isn't `/realms/{r}/theme/assets/...` or an allowlisted image origin
- enforce all of this on save, on import, and when loading legacy data;
- log a warning and skip the CSS if stored CSS no longer validates;
- show a notice in the admin API that custom CSS depends on internal markup and may break across
  versions. Recommend the theme model instead.

### 5. File-based themes (optional, for operators)

- `helix.theme.directory` points at a mounted directory, for example a ConfigMap or a volume:
  `themes/{themeName}/theme.json` (same schema as the model), with `assets/` alongside.
- A realm can select `themeName` instead of, or as a base for, database settings; database fields
  override file values.
- File themes go through the same validation at startup and on reload. A failing theme is refused
  with a clear log, and the realm falls back to its database theme or the default.
- The Helm chart gets a `themes` value (ConfigMap or existing volume) to mount it.

### 6. CSP tightening (after 2 and 4)

With no inline style blocks left:
- remove `'unsafe-inline'` from `style-src`;
- restrict `img-src` to `'self' data:` plus the realm's allowlisted image origins, applied per realm.

Check every template still renders without inline `style=""` attributes; move any to classes.

### 7. Admin API, import/export and migration

- `GET`/`PUT /admin/realms/{r}/theme`
  - `PUT` returns field-level validation errors.
- `GET`/`PUT /admin/realms/{r}/organizations/{orgId}/theme`
- `POST /admin/realms/{r}/theme/preview`
  - Returns a rendered login page with the proposed theme, without saving it.
- `POST` / `GET` / `DELETE /admin/realms/{r}/theme/assets`
- Permissions:
  - reading and writing the theme needs `manage-realm`;
  - organization themes need `manage-organizations`.
- Every change is audited (fields changed, never asset bytes).
- Realm import/export includes the theme and asset references; asset bytes go in an optional archive
  export.
- Flyway migration:
  - move `primaryColor`, `backgroundColor`, `logoUrl` and `welcomeText` into the new model;
  - keep valid legacy `customCss` as the escape hatch;
  - don't serve invalid legacy CSS, and log it clearly.
- Keep the old realm-settings fields working for one minor version, mapped to the theme, and mark them
  deprecated in the API docs.

## Tests (write them first)

- **Coverage.** A parameterised test renders every user-facing template for a realm with a full theme.
  It asserts the theme stylesheet link, favicon, logo and texts are present and that there is no
  HelixIAM default text. A new template without the fragment fails the test.
- **Validation.** Bad colours, low-contrast pairs, non-https URLs, oversize or wrong-type assets,
  malicious SVGs, and every forbidden custom-CSS construct are rejected on save and on import.
- **Security.**
  - A realm admin can't get script executed on any page through any theme field.
  - The CSP header has no `'unsafe-inline'` for styles.
  - `img-src` blocks non-allowlisted origins.
  - Organization themes can't be read or changed across realms (the rc.4 cross-realm rules).
- **Precedence.** The organization theme overrides the realm theme per field only when an organization
  is in context.
- **Caching.** `theme.css` has an ETag, and it changes when the theme changes.
- **File themes.** A mounted theme is used. An invalid one falls back and is logged.
- **Emails.** Verification and reset emails use the theme's logo, colours and texts.
- **Migration.** Legacy settings are carried over, and invalid legacy CSS is dropped with a log.

## Done when

- A realm configured only through `PUT /admin/realms/{r}/theme` looks fully branded, light and dark, on
  every user-facing page and email, with its own fonts and favicon and no HelixIAM wording.
- The same realm themed from a mounted file theme looks identical.
- The CSP has no `style-src 'unsafe-inline'`, and `img-src` is restricted.
- `docs/THEMING.md` documents the model, the CSS variables contract, the escape hatch and its limits,
  and file themes.
- Full test suite green. Changelog entry, with the security improvement called out.
