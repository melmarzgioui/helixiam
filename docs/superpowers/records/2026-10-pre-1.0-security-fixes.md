## 1. Federated logins skip the post-broker MFA step-up (`633d944`)

**Root cause.** The realm's seeded `browser` flow gates `otp` behind the `mfa-enabled` condition (`MfaEnabledCondition`), and that condition read the user from the `SecurityContext`. `FederatedLoginCompleter.complete()` runs `flowExecutor.begin()` before it persists any authentication, so the context was empty. The condition returned "MFA not enabled", the flow COMPLETED, and `persist(fullAuthentication)` created a full session for a user with TOTP enrolled. The local path (`FlowLoginSuccessHandler`) puts `MfaAuthentication` into the context before `begin()`, which is why only brokered logins were affected. The rc.5 `MfaEnforcementFilter` still re-gated `/oauth2/authorize`, the SAML SSO endpoint and the account console, so a relying party never got a code. The session itself was full, though, and any other surface trusted it.

**Fix.** `MfaEnabledCondition` now evaluates the flow's own user, `AuthenticationContext.userId()`, which comes from `FlowExecutionState.userId()`. It uses the pending principal when that principal is the same user. Otherwise it loads the user by id through `FederatedIdentityPublisher.loadUser`, the same lookup the broker uses. A flow user that cannot be loaded throws, which fails the flow instead of skipping the step. Only a flow with no user yet falls back to the principal, which is the old behaviour.

I checked the other conditions and authenticators. `RiskAuthenticator` already uses `context.userId()`. The only other flow code that read the context was `TotpOtpVerifier`, which ignored its `userId` argument and verified against whatever principal was there. It now refuses a principal that is not the flow's user.

**Tests.**
- `MfaEnabledConditionTest` (new, 6 tests).
- `TotpOtpVerifierTest` (new, 3 tests).
- `FederatedLoginCompleterTest`: two new tests run the real `FlowExecutor` with the seeded browser-flow shape.
- `FederatedMfaStepUpBrowserE2eTest` (new, Playwright, uses the `e2e-stub` broker callback):
  - an enrolled user in a realm that does not require MFA stops at `/flow`;
  - the relying party gets no code, and a fresh authorize request mid-step gets none either;
  - after the code is entered on `/flow`, the relying party gets a code;
  - a user without MFA completes at once.
- The existing local-login MFA tests (`MfaE2eTest`, `MfaGateBrowserE2eTest`, `SamlMfaGateBrowserE2eTest`) were not edited and stay green.

**RED.**
- Unit tests: 5 of 14 failed.
  - `withNoPrincipal_theFlowsMfaUser_isChallenged`: expected SUCCESS.
  - `thePrincipalOfAnotherUser_doesNotDecide`: expected SUCCESS.
  - `aFlowUserThatCannotBeLoaded_failsClosed`: expected a throwable.
  - `TotpOtpVerifierTest.aPrincipalOfAnotherUser…`: expected false, was true.
  - `aBrokeredLoginOfAnMfaUser_stopsAtTheSecondFactor_withoutAFullSession`: expected `redirect:/flow`, got `redirect:https://helix.test`, meaning a full session was created.

## 2. `EidLevelOfAssurance.meetsMinimum` treats an unknown minimum as met (`676fcc5`)

**Root cause.** `rung(minimum)` mapped an unknown value to 0, and `meetsMinimum` checked `rung(asserted) >= 0 && rung(asserted) > 0`, so any recognised asserted level passed. It got worse: the console stores short keywords (`loa1`–`loa4`, `low/substantial/high`), and the backend never mapped them. Every eID connection created with the console's default `loa3` therefore had an "unknown" minimum and accepted every level. The same keyword was also sent as the AuthnRequest's `RequestedAuthnContext` class ref.

**Fix.**
- An unrecognised non-blank minimum is never met. A blank or null minimum still means "no minimum".
- The console keywords map to the scheme's URN (`EidLevelOfAssurance.canonicalMinimum`, `isValidMinimum`).
- Validation at the admin write path: `IdentityProviderAdminController` create and update return `400 {message, fieldErrors.minimumLoa}` through `ProviderValidationException` and `AdminValidationAdvice`, never a 500. An unknown eID scheme gives `fieldErrors.scheme`.
- Validation at provider build: `FederationProviderFactory.fromStored` and `build(properties)` throw `IllegalArgumentException("… minimumLoa is not a known … level of assurance")`. The registry refresher already skips a malformed stored provider with a warning; a bad `helix.federation.eid` entry fails startup.
- The canonical URN is stored in `EidProviderConfig` (new `withMinimumLoa`), so the AuthnRequest now asks for the real URN.
- `EidScheme.of(protocol, override)` and `isEidProtocol` are shared by the factory and the controller.

**Tests.**
- `EidLevelOfAssuranceTest`: 3 new tests covering an unknown minimum never being met, keyword mapping, and valid/blank minimums.
- `FederationProviderFactoryTest`: 3 new tests covering rejection on both paths and keyword→URN. Two existing fixtures used non-ladder values (`urn:loa`, `…LoA:Substantieel`) and now use `…LoA:Substantial`.
- `IdentityProviderAdminControllerTest`: 4 new tests, including a standalone MockMvc test with the advice asserting a 400 with `$.fieldErrors.minimumLoa`.

**RED.** 9 of 32 failed. For example, `anUnrecognisedMinimumIsNeverMet` was true where false was expected, the factory tests got no throwable, and the MockMvc test got 201 instead of 400.

**GREEN.** 54 of 54 passed, including the eID provider and validator suites.

**Operator impact.** A stored eID connection whose `minimumLoa` is neither blank, a ladder URN nor a known keyword (for example a custom URN such as `…LoA:Substantieel`) is now skipped at load with a warning, and its sign-ins stop. Fix it in the console; a save with an unknown value gets a field error. Connections using the console's built-in options keep working and are now actually enforced.

## 3. `AttributeEncryption` returns undecryptable values unchanged (`c419a9a`)

**Root cause.** When decryption failed, `convertToEntityAttribute` tried GCM, then the legacy `AES` (ECB) format with the same key bytes, and then `return data`. A plaintext row, a value written under another key, or an altered value was therefore read as the secret. Affected columns: `UserCredentials.mfaSecret`, `HotpCredentialEntity.secret`, `RealmKey.privateKey`, `ServiceProviderOAuthClient.clientSecret`, `WebhookSubscription.secret`, `ScimTarget.token`, `MessagingProvider.secret`, the `SamlRelyingPartyEntity` signing and encryption certificates, and the bodies in `JdbcEmailRetryStore`.

**Fix.** Only the final fallback changed; the GCM path and the legacy AES path are unchanged. An undecryptable value now throws `IllegalStateException("An encrypted database column could not be read: <cause>.")`. The cause is one of:
- "not encrypted (written before DB_ENCRYPTION was set) … set helix.allow-plaintext-secrets=true …";
- "cannot be decrypted with the current DB_ENCRYPTION key (the key changed, or the value was altered)".

It picks between them with a base64 and length heuristic. The value never appears in the message.

The migration path reuses the existing opt-out, `helix.allow-plaintext-secrets` (`HELIX_ALLOW_PLAINTEXT_SECRETS`, default false), instead of adding a new property:
- When it is true and `DB_ENCRYPTION` is set, undecryptable values are read as stored.
- `PlaintextReadLogger`, a new Hibernate `Interceptor` registered through a `HibernatePropertiesCustomizer`, matches the loaded entity state by identity against those reads. It logs WARN `Read a plaintext value from encrypted column <Entity>.<attribute> …`, never the value.
- The value is encrypted on the entity's next write.

`ProductionReadinessCheck` follows that opt-out's existing convention (allowed outside dev, listed as insecure), so key plus flag is a WARN, not a FATAL. The converter gained an `@Autowired` two-argument constructor. The one-argument constructor, used by `EmailDeliveryConfig`, fails closed. Documented in `application.properties`, the README configuration table and `CHANGES-1.0.md`.

**Tests.** `AttributeEncryptionTest` (new, 10 tests):
- current-format round trip;
- wrong key throws, and the message holds neither the value nor the ciphertext;
- tampered value throws;
- plaintext row throws by default, naming the cause and the flag;
- plaintext row is read with the flag, recorded, and re-encrypted on the next write;
- legacy AES/ECB ciphertext still decrypts;
- no key passes values through;
- the one-argument constructor fails closed;
- null stays null;
- the interceptor names the attribute.

`ProductionReadinessCheckTest` gains a test that key plus flag is not fatal.

**RED.** 7 of 11 failed: the wrong-key, tampered, plaintext and one-argument cases got no throwable, and the plaintext read was not recorded. The round trip, legacy format and no-key tests already passed. The 11th test asserted "wrong key still throws with the flag on"; I dropped it because the flag must read every undecryptable value (see the concerns).

**GREEN.** 10 of 10 passed. `EmailRetryQueueE2eTest`, `MfaE2eTest` and `BootstrapServiceAccountE2eTest` pass, and both schema runs load seeded data.

**Operator impact (breaking).** If a deployment ran without `DB_ENCRYPTION`, then set it, and still has rows written before that, those reads now fail. This includes the realm signing key, so sign-in is affected. Set `HELIX_ALLOW_PLAINTEXT_SECRETS=true` until the rows are rewritten, then unset it. A changed `DB_ENCRYPTION` key now fails loudly instead of returning ciphertext as the secret.

## 4. Client IP from client-controlled `X-Forwarded-For` (`b96284c`)

**Root cause.** `RateLimitFilter`, `AuditContext.clientIp` (used by about 12 audit and magic-link call sites), `RiskSignalGatherer`, `RegisterUserController` and `ResetPasswordController` each took the left-most `X-Forwarded-For` (and in two cases `X-Real-IP`) from any client. In addition, `server.forward-headers-strategy=framework` installs Spring's `ForwardedHeaderFilter`. Its wrapper returns the left-most XFF entry as `getRemoteAddr()` and hides the header, so even plain `getRemoteAddr()` was spoofable.

**Fix.** There is now one `ClientIpResolver` (`io.helixiam.authorization.security.net`, a `@Component`), and every call site goes through it: the filter and the gatherer by injection, the static helpers through `ClientIpResolver.current()`, which the bean installs.
- **Peer address.** It reads `getRemoteAddr()` from the container's own request, unwrapping `ServletRequestWrapper`s and so getting beneath the `ForwardedHeaderFilter` wrapper.
- **Trusted proxies.** Forwarded headers count only when that peer is in `helix.security.trusted-proxies` (`HELIX_TRUSTED_PROXIES`): comma-separated IPs or CIDRs, IPv4 or IPv6, default empty. An invalid entry fails startup.
- **The walk.** From a trusted peer, all XFF lines are walked from the right, and the first address that is not a trusted proxy is the client. A malformed hop stops the walk at the last trusted address. If every hop is trusted, the left-most is the client. `X-Real-IP` is honoured only from a trusted peer that sent no XFF.
- **Parsing.** Values are parsed strictly as IP literals (`[v6]:port` and `v4:port` are accepted, zone ids are stripped); a host name is never resolved.

**Why the resolver and not `RemoteIpValve`/NATIVE.** I kept `forward-headers-strategy=framework` for `X-Forwarded-Proto`/`-Host`/`-Port`, which drive `isSecure()`, the issuer and absolute redirects, and made the resolver the only source of the client IP. Switching to NATIVE with `server.tomcat.remoteip.internal-proxies` would also make Tomcat ignore `X-Forwarded-Proto` from any peer outside the list. Tomcat's default list covers all RFC1918 ranges, which in Kubernetes means any pod. Narrowing it to an empty default would turn every TLS-terminated deployment into `http` issuers and insecure cookies until the operator configures it. That is a much larger break, and it would put two layers in play that could disagree. Because the resolver reads beneath the framework filter, the two layers cannot disagree about the client IP: nothing uses the filter's `getRemoteAddr()` for it any more.

**Deployment check.**
- The Helm chart has no bundled proxy, but an optional Ingress. I added `config.trustedProxies` → `HELIX_TRUSTED_PROXIES`, a values comment, a chart README section, and a NOTES.txt warning when `ingress.enabled` is true and the list is empty.
- docker-compose publishes the server directly on `:8080`, so the default (no trust) is correct. Only console-proxied admin and login traffic shows the console container's IP. I did not trust the compose subnet, because the published port arrives from the bridge gateway in that same subnet, which would let clients on the host spoof XFF.
- The console nginx appends `$proxy_add_x_forwarded_for`, which the right-to-left walk handles.
- README: a new "Client IP behind a reverse proxy" section, and the rate-limit text is updated.

**Tests.**
- `ClientIpResolverTest` (new, 11 tests): the default ignores XFF and X-Real-IP; spoofed XFF from an untrusted peer is ignored; a trusted proxy is honoured; the right-most-untrusted walk, including multiple header lines; all hops trusted; X-Real-IP only from a trusted peer; IPv6 (CIDR, bracketed with port, IPv6 peer); IPv4 with port; malformed hops, empty and blank lists, and a host name; reading beneath a real `ForwardedHeaderFilter`; an invalid config fails; a null request.
- `RateLimitFilterTest`: a spoofed XFF from an untrusted peer does not buy a new budget. The old `honoursXForwardedFor_forPerIpBudget` encoded the vulnerable behaviour, so it now uses a trusted-proxy resolver.
- `AuditContextClientIpTest` and `RiskSignalGathererTest` (new).

**RED.** With the resolver stubbed as the old first-hop algorithm, 11 of 20 failed:
- rate limiter: expected 429, got 200;
- audit: expected `198.51.100.20`, got the spoofed address;
- risk: expected `198.51.100.20`, got the spoofed address;
- 8 resolver tests failed.

**GREEN.** 30 of 30 passed in the targeted run, and 79 of 79 in the related rate-limit, audit, risk, CAPTCHA, register and reset classes.

**Operator impact (breaking).** Behind any reverse proxy, ingress or load balancer, `HELIX_TRUSTED_PROXIES` (Helm: `config.trustedProxies`) must be set to the proxy's source addresses. Otherwise every request appears to come from the proxy: all clients share one sign-in rate-limit bucket (20 per minute by default, so a real denial-of-service risk), and the audit log and risk signals record the proxy's IP.

## B. Forwarded host and proto only from trusted proxies (`895c0c2`)

**Root cause.** `server.forward-headers-strategy=framework` registers Spring's `ForwardedHeaderFilter` for every request. The OIDC issuer is derived from the request (no fixed issuer is configured, in production or in e2e). One unauthenticated request with `X-Forwarded-Host: evil.example` and `X-Forwarded-Proto: https` got a discovery document with `"issuer": "https://evil.example/evil/realms/master"`. The same headers steered `isSecure()`, redirects and absolute URLs.

**Fix.** `TrustedProxyForwardedHeaderFilter` extends `ForwardedHeaderFilter`. `ForwardedHeadersConfig` registers it as `FilterRegistrationBean<ForwardedHeaderFilter>`, so Boot's `@ConditionalOnMissingFilterBean` backs off. It keeps Boot's order (`HIGHEST_PRECEDENCE`) and dispatcher types (REQUEST, ASYNC, ERROR), and it is active only for the `framework` strategy.
- If the TCP peer is in `helix.security.trusted-proxies` (checked by `ClientIpResolver.isTrustedPeer`), Spring's normal processing applies.
- Otherwise the request goes through a `ForwardedHeaderFilter` in remove-only mode: the forwarded headers are stripped and ignored.
- There is still only one trust list, shared with the client-IP resolver.
- A startup WARN fires when `IDP_BASE_URL` is https and the list is empty.
- Docs updated: README "Client IP behind a reverse proxy", `application.properties`, Helm `values.yaml`, chart README and NOTES (the ingress warning now covers the http issuer), and `CHANGES-1.0.md`.

**Tests.**
- `TrustedProxyForwardedHeaderFilterTest` (new, 4 tests):
  - from an untrusted peer, `isSecure()`, scheme, host, port, request URL and redirect `Location` are unchanged, and the headers are hidden;
  - from a trusted peer, X-Forwarded-* are applied (https, evil.example, prefix, absolute redirect);
  - a trusted RFC 7239 `Forwarded` header is applied;
  - with an empty list, nothing is honoured.
- `ForwardedHeadersTrustE2eTest` (new, real context, 127.0.0.1 untrusted):
  - the discovery issuer stays `http://localhost:<port>/realms/master`;
  - the sign-in redirect from `/realms/master/account` holds neither `evil.example` nor `https:`;
  - the only registered `ForwardedHeaderFilter` is the trust-checking one.
- The existing `MagicLinkE2eTest` attacker-host test still passes.

**RED.** The filter was stubbed as plain Spring behaviour.
- Unit test: `isSecure()` was true for an untrusted peer.
- E2e: the issuer was `https://evil.example/evil/realms/master`, the redirect followed the headers, and Boot's filter was in use.

**GREEN.** All 18 targeted tests pass. A control run of the e2e test with `-Dhelix.security.trusted-proxies=127.0.0.1,::1` fails exactly as expected (issuer `https://evil.example/evil/...`). That proves a trusted proxy's headers are honoured end to end, which is the ingress case with trusted proxies set.

**Operator impact (breaking).** Behind a TLS-terminating ingress or load balancer, `HELIX_TRUSTED_PROXIES` (Helm: `config.trustedProxies`) is now required. Without it the server sees plain HTTP: request-derived issuers and redirects become `http://`, and clients validating `iss` break. The session cookie's Secure flag is pinned, so it is unaffected. docker-compose is unaffected: the console nginx passes `Host $http_host`, and nothing there terminates TLS.

### R1. No full session before enrolment, and session rotation (`2b0d805`)

`MfaEnrolmentRequirement.mustEnrol(realm, userId)` is true when the realm requires MFA and the user is not enrolled in TOTP. The same rule now applies on these paths:

### R5. Host allow-list and the http-behind-https ERROR (`ecc64ec`), BREAKING

`HostAllowListFilter` is registered at order `HIGHEST_PRECEDENCE + 1`, right after the trusted forwarded-header filter, so a trusted proxy's `X-Forwarded-Host` is what it checks. It is off in `dev`.

**Allowed hosts.** The hosts of `IDP_BASE_URL` and `SP_BASE_URL`, plus `HELIX_ALLOWED_HOSTS` (`helix.security.allowed-hosts`). Matching is case-insensitive and ignores the port. Any other host gets `400 Unknown host.` before anything derives an issuer or URL.

I included the `SP_BASE_URL` host deliberately: the console's nginx proxies `/admin`, login and OAuth calls with `Host` set to the console's own host. Without it, every console whose host differs from the IdP's would break.

**Probes.** I checked how they call the server:
- the Helm probes are kubelet `httpGet` on `port: http`, which sends `Host: <podIP>:<port>`;
- the Dockerfile `HEALTHCHECK` curls `http://127.0.0.1:$PORT/actuator/health/readiness`;
- docker-compose has no healthcheck for the server.

So these are always allowed:
- a host equal to the address the connection arrived on (`getLocalAddr()`, which covers kubelet and Prometheus by pod IP, and in-cluster callers by pod IP);
- `localhost` from a loopback peer;
- `/actuator/health/**` with any host (it builds no URLs).

In docker-compose, `IDP_BASE_URL` and `SP_BASE_URL` are both on `localhost`, and the console's nginx sends `Host $http_host` (`localhost:8090`), so compose keeps working.

**ERROR log.** When `IDP_BASE_URL` is https and an allowed-host request arrives over plain http, the filter logs an ERROR at most once a minute, telling the operator to set `HELIX_TRUSTED_PROXIES`. Probes never trigger it. The SAS issuer is **not** pinned.

- Helm: new `config.allowedHosts` → `HELIX_ALLOWED_HOSTS`. NOTES now warn whenever `config.trustedProxies` is empty, mention load balancers, Gateway API and meshes, and list the answered hosts.
- README: a Host allow-list paragraph and the "only `framework`" note.

## P. Re-spelled login path vs the sign-in rate limit (`22889b9`): did not reproduce

**Hypothesis.** `RealmRoutingFilter` passes the raw, still percent-encoded remainder on as the servlet path, and `RateLimitFilter` matches on it. So `/realms/master/l%6Fgin` would skip the sign-in limit while Spring MVC still routes it to the login.

**Probe.** I ran a real isolated boot with a login budget of 3 and non-Secure cookies over http, and posted wrong passwords with a valid CSRF token, 8 times per spelling:

| Spelling | Statuses | Meaning |
|---|---|---|
| `/realms/master/login` (control) | 302 ×3 (`login?error`), then 429 | processed, then throttled |
| `l%6Fgin` and `%6C%6F%67%69%6E` | 400 ×8 | not counted by the limiter, refused by Spring Security's `StrictHttpFirewall` ("potentially malicious String \"%\"", confirmed directly against `StrictHttpFirewall`) |
| `login;x=1` | 400 ×3, then 429 | `;` is refused by the firewall |
| `/./login`, `//login` | 400 | refused |
| `master%2Flogin`, `login%3Bx=1` | 400 | refused |
| `LOGIN` | 401 ×8 | not the login endpoint |
| `login/` | 401, then 429 | not the login endpoint |
| `m%61ster/login` | 404 | unknown realm |

**Conclusion.** No spelling gets a sign-in attempt processed beyond the budget. The limiter does not count the encoded spellings, but the firewall, which runs for every request in `FilterChainProxy` before any handler, refuses them. Following the instructions, I recorded this and added a regression guard instead of changing code.

**Test.** `LoginRateLimitPathEncodingE2eTest` (11 spellings) asserts that no spelling answers more than 3 sign-in attempts, and that the canonical path is processed 3 times and then gets 429.

**Residual.** The protection depends on `StrictHttpFirewall` staying strict. If someone relaxes it (allowing `%` or `;`), `RateLimitFilter` and `RealmRoutingFilter` would need to match on the decoded, normalised path, and this test would catch the regression.

## Concerns and out of scope (not changed)

- The connection detail page in the console, unlike the wizard, has no custom-LoA input. The DigiD workaround is reachable through the wizard or the admin API.
- Host allow-list: relying parties or tools that reach the server by an in-cluster service name, or any host other than the IdP and SP hosts, now get 400 until that name is in `HELIX_ALLOWED_HOSTS`. A per-realm issuer pinned to another host needs the same.

- The spoofed `getRemoteAddr()` from Spring's forwarded handling now only applies to trusted peers (follow-up B), where it gives the left-most XFF. Spring Security's `WebAuthenticationDetails` still records that address rather than the resolver's.
- The legacy AES/ECB fallback can, with roughly 1/256 probability, "decrypt" a value under the wrong key because the padding happens to be valid, and return garbage. It is pre-existing and kept so legacy rows still decrypt.
- In migration mode (`HELIX_ALLOW_PLAINTEXT_SECRETS=true` with a key), a changed key is also hidden, because ciphertext is returned as stored. This is documented, and the readiness check flags it.
- Pre-existing: `database.encryption=${DB_ENCRYPTION:}` injects `""`, not null, so `AttributeEncryption` would get an empty-key `SecretKeySpec`. The "no key + `HELIX_ALLOW_PLAINTEXT_SECRETS`" mode may not start. Not verified or changed.
- `MfaEnabledCondition` now depends on `FederatedIdentityPublisher` for the by-id lookup. The name is federation-specific, but it is the same passwordless by-id load the broker already uses. I avoided `UserAdminPublisher.get`, because it requires a tenant link, and JIT-provisioned federated users have none.
