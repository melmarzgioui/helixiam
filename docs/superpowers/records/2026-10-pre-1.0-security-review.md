# Security review: `fix/pre-1.0-security` (6 commits on `c2ad6a0` / v1.0.0-rc.7)

Reviewer: independent, read-only. No code was changed.
Scope: `git log -p origin/master..HEAD`, `SECURITY-FIXES-REPORT.md`, and the top section of `CHANGES-1.0.md`, plus
the surrounding code each fix depends on.
Targeted unit tests were re-run offline and pass: `ClientIpResolverTest`, `TrustedProxyForwardedHeaderFilterTest`,
`MfaEnabledConditionTest`, `TotpOtpVerifierTest`, `AttributeEncryptionTest`, `EidLevelOfAssuranceTest`,
`FederatedLoginCompleterTest` and `RateLimitFilterTest`.

## Verdict: Needs fixes (small)

All six fixes are correct for the bug they target. None of them can be bypassed in the way it was reported. None of
them weakens an existing test.

Three gaps should close before the release candidate:
1. Federated sign-in still creates a full session when the realm requires MFA but the user has not enrolled (finding 1).
2. Reusing `HELIX_ALLOW_PLAINTEXT_SECRETS` can switch on the plaintext-read mode without anyone noticing (finding 4).
3. Behind a TLS ingress, an rc.7 → rc.8 upgrade breaks every relying party, and only a WARN line says so (finding 5).

Everything else is Minor or pre-existing.

## Findings

| # | Sev | Where | Finding |
|---|---|---|---|
| 1 | Important | `federation/FederatedLoginCompleter.java:98-99` | Realm requires MFA, user not enrolled: the flow's `mfa-enabled` condition reads only `user.isMfaEnabled()`, so the flow COMPLETES and `persist(fullAuthentication)` creates a **full session before any MFA**. Only the authorize, SAML and account gates send the user to `/mfa/enable`. The commit's claim "no session before MFA passes" holds only for enrolled users. `MagicLinkController.verify` (lines 133-136) already does this right (`enrolled \|\| mfaPolicy.required(realm)` → `MfaAuthentication` + `/mfa/enable`). Mirror it in the COMPLETED branch. The local password path has the same gap, so this is parity, not a regression. |
| 2 | Important | `federation/FederatedLoginCompleter.java:93-99` / `FederatedSessionEstablisher.persist` | The federated sign-in neither rotates the session id (`request.changeSessionId()`) nor clears `MfaSessionState`. Magic-link sign-in does both. The session that carried the broker `state` becomes the authenticated session (fixation), and a stale `HELIX_MFA_VERIFIED_USER` for the same user survives into the new sign-in. This is pre-existing, but it is in the same code path the MFA fix touches. |
| 3 | Minor | `security/flow/MfaEnabledCondition.java:61` | The by-id lookup (`FederatedIdentityPublisher.loadUser` → `findByUserId`) is not realm-scoped. The id comes only from server-side flow state, which the broker resolved realm-checked, so this cannot be exploited today. Add a realm check if `loadUser` gains another caller. `state.userId` cannot be changed by the client: it is set by the completer or handler, or by an authenticator's `establishUser` on a proven factor. |
| 4 | Important | `persistence/security/AttributeEncryption.java:171-178`, `common/startup/ProductionReadinessCheck.java:92` | The plaintext-read migration mode reuses the existing `HELIX_ALLOW_PLAINTEXT_SECRETS`. An operator who set that flag earlier to start without a key, and later added `DB_ENCRYPTION`, is now **silently** in migration mode. Undecryptable values (including a changed key or a planted plaintext TOTP seed or client secret) are read as stored. The only signal is one entry in the readiness WARN list. Use a dedicated flag (e.g. `HELIX_ENCRYPTION_MIGRATION_READ_PLAINTEXT`), or at least log a multi-line banner per boot plus a WARN on every plaintext read (`PlaintextReadLogger` only fires when the identity match succeeds). |
| 5 | Important | `security/net/ForwardedHeadersConfig.java:33-36`; Helm `values.yaml` `trustedProxies: []` | The default for TLS-terminated deployments is not safe: after upgrading, every request-derived issuer turns `http://` and all relying parties fail `iss` validation. The README, the chart README, `values.yaml`, NOTES.txt and CHANGES document this well. But the server only logs a WARN, and NOTES only fires when the chart's own `ingress.enabled` is set, which misses an external LB or Gateway API. Recommend: outside `dev`, fail startup (or add a FATAL readiness item) when `IDP_BASE_URL` is https, the list is empty, and the first request's scheme is http. Alternatively, mark it **BREAKING** at the top of the release notes, with the per-realm `issuer` pin (`RealmSettings.issuer`) as the documented escape hatch. |
| 6 | Important | `security/net/TrustedProxyForwardedHeaderFilter.java` (scope) | The `X-Forwarded-Host` vector is closed, but the request-derived issuer is still taken from the **`Host` header** itself. With the server reached directly (the docker-compose default `:8080`), `Host: evil.example` gives `issuer: http://evil.example/realms/master`. This is not cacheable by the server itself, so the impact is limited to shared caches and CDNs, but the same attack class remains. Document "pin the realm issuer or put a Host-validating proxy in front", or validate `Host` against `IDP_BASE_URL`. |
| 7 | Important | `federation/eid/EidLevelOfAssurance.java:52` | eHerkenning `loa2plus` is rung 2, the same as `loa2`. A minimum of `loa2plus` (accepted by the new keyword map) is therefore met by a plain `loa2` (EH2) assertion: fail-open by one notch. The ladder entry is pre-existing, but this commit newly makes `loa2plus` a validated, accepted minimum keyword. Give EH2+ its own rung (e.g. scale the rungs ×10). |
| 8 | Important | `federation/eid/EidSamlIdentityProvider.java:245-251`; `CHANGES-1.0.md:45-49` | Classic DigiD: the AuthnRequest still sends `RequestedAuthnContext` `urn:nl-eid-gdi:1.0:LoA:Substantial` (Comparison=minimum), which a Koppelvlak endpoint will most likely answer with `NoAuthnContext` or refuse. This is no worse than before, when the raw `loa3` was sent. A working path exists: store the oasis class (e.g. `…ac:classes:Smartcard`) as the minimum via the console's custom-LoA field. It is valid on the ladder now, and it is both requested and compared. But that path appears **nowhere** in CHANGES, the README or the console. Document it in the CHANGES eID entry, or add a per-connection "request class" or "classic DigiD" variant. The oasis mapping (PPT=Basis, MobileTwoFactorContract=Midden, Smartcard=Substantieel, SmartcardPKI=Hoog) matches the reviewer's understanding of the Logius Koppelvlak spec. Confirm it against the current Logius document before 1.0. The `urn:nl-eid-gdi:1.0:LoA:*` URNs on the existing DigiD ladder are themselves unverified: CombiConnect and routing services usually assert eIDAS `…/LoA/NotNotified/*` URIs. |
| 9 | Minor | `controller/admin/io/RealmImportService.java:734` | Realm import writes IdP configs without `validateEid`, so a bad `minimumLoa` imports successfully and only shows up as a "Skipping malformed …" WARN at registry refresh. This fails closed, but the operator sees no error. |
| 10 | Minor | `persistence/security/AttributeEncryption.java:156-163` | The legacy AES/ECB fallback still runs on every GCM failure. A wrong-key or tampered value whose decoded length is a multiple of 16 has about a 1/256 chance of passing PKCS#5 padding, and garbage is then returned silently. This happens for GCM ciphertexts with plaintext length ≡ 4 (mod 16), and for long plaintexts. The impact is a corrupted secret (it fails to verify), not a bypass. Consider trying ECB only when the length is not GCM-shaped, or checking that the result is printable UTF-8. |
| 11 | Minor | `src/main/resources/application.properties:68` (pre-existing) | `database.encryption=${DB_ENCRYPTION:}` injects `""`, so `password == null` never holds. With the key unset, `new SecretKeySpec(new byte[0], "AES")` throws `IllegalArgumentException: Empty key` (the reviewer checked this in jshell). The documented "no key + `HELIX_ALLOW_PLAINTEXT_SECRETS`" mode therefore cannot start, and the "no key passes values through" unit test covers a branch that production never reaches. Use `${DB_ENCRYPTION:#{null}}` or treat a blank key as null. |
| 12 | Minor | `persistence/security/AttributeEncryption.java:52-53` | `PLAINTEXT_READS` is a never-removed `ThreadLocal`. In migration mode, up to 64 plaintext secret strings stay referenced from pooled threads. Clear it at the end of a request or transaction. |
| 13 | Minor | `security/net/ClientIpResolver.java:92` | `X-Real-IP` is still honoured from a trusted peer that sent no XFF. If the trusted proxy neither sets nor strips `X-Real-IP` (an L4 LB, or an ingress with XFF disabled), the client chooses its own IP. Drop `X-Real-IP`, or document that the proxy must overwrite it. No untrusted path reads it. |
| 14 | Minor | `security/net/ClientIpResolver.java:106` + docs | Inherent to right-most-untrusted: if the trusted list overlaps addresses that clients use (e.g. `10.0.0.0/8` with in-cluster callers), those clients can prepend any address. The docs say "never list ranges clients can connect from", which is fine. An IPv4-mapped peer (`::ffff:a.b.c.d`) is normalised by the JDK to `Inet4Address` and matches v4 ranges correctly. A v4-mapped **CIDR in the config** (`::ffff:10.0.0.0/104`) becomes a 4-byte address with prefix 104 and fails startup with a misleading "not an IP or CIDR" message. Malformed, blank, empty and all-trusted XFF lists, and multiple header lines, are all handled correctly. |
| 15 | Minor | `security/net/ForwardedHeadersConfig.java:30` | The filter is active only for `forward-headers-strategy=framework`. An operator who switches to `native` gets Tomcat's `RemoteIpValve` with the default RFC1918 internal-proxy list. The valve rewrites the container request, so `ClientIpResolver` would then see the valve's XFF-derived address. Mention in the README that only `framework` is supported. |
| 16 | Minor | `security/flow/FlowController.java` (pre-existing) | After `/flow` completes, `mfaService.unlockUser()` promotes the original principal, not `state.userId()`. With the new verifier check, a TOTP step can no longer be passed against another user. In an admin-built flow where a later `establishUser` switches users, though, the promoted principal and the flow user could still differ. Assert that they match before promoting. |

## Per-commit assessment

**676fcc5 (eID minimum LoA): correct.** An unknown non-blank minimum gives `false`, and blank still means "no
minimum". The keywords are canonicalised once, at build time (`requireMinimumLoa`). The resulting URN is used both
in the AuthnRequest (`EidSamlIdentityProvider:247`) and in the comparison (`OpenSamlEidAssertionValidator:105`).
`meetsMinimum` canonicalises again, which is harmless. The admin create and update calls answer 400
`fieldErrors.minimumLoa` or `fieldErrors.scheme`, and the console sends eID schemes as `protocol`
(`helix-dashboard/src/api/client.ts:55`), so the validation does fire. Nothing in this commit fails open, apart from
the `loa2plus` rung (finding 7). Gaps: findings 7 and 9.

**c419a9a (AttributeEncryption): correct with caveats.** It fails closed by default. The exception text contains no
value or ciphertext, and a test asserts this. The startup realm-key path (`KeyMaterialService` →
`RealmKeyService.getOrCreateActive`) throws from inside the repository load, so `orElseGet(generateActive)` cannot
silently regenerate a key. `JdbcEmailRetryStore` catches the exception and drops the row. Gaps: findings 4, 10, 11
and 12.

**b96284c (ClientIpResolver): correct and complete.** Grepping `src/main` for `X-Forwarded`, `X-Real-IP`,
`getRemoteAddr` and `getRemoteHost` finds every reader routed through the resolver. That covers rate limiting,
`AuditContext` (about 12 call sites), the risk gatherer, CAPTCHA register/reset, and the workload-identity rate key
(via `AuditContext`). Nothing reads `WebAuthenticationDetails`. CIDR math, v4/v6 parsing, port and zone stripping are
correct, and parsing never resolves DNS (the JDK's bracketed-literal path was verified). Gaps: findings 13, 14 and 15.

**633d944 (federated MFA): correct for enrolled users.** There is one broker entry point,
`FederationBrokerController.handleCallback`, and every brokered login reaches the completer through it: OIDC, SAML
(including IdP-initiated, which uses the same callback), eID, and the test-only `e2e-stub`. The account console has
no account-linking endpoint and there are no wallet hooks. LDAP runs through the password chain. For an enrolled
user, the session holds only an unauthenticated `MfaAuthentication` until `/flow` passes, and the browser e2e test
shows that a fresh `/authorize` call gets no code in that window. A user who cannot be loaded fails closed (the
exception is thrown before anything is persisted). Gaps: findings 1, 2, 3 and 16.

**7d2a1e0 (classic DigiD classes): adds no fail-open.** The oasis classes are confined to the DIGID ladder. The new
tests confirm that eHerkenning and eIDAS give them rung 0. Interop and documentation: finding 8.

**895c0c2 (trusted forwarded headers): correct.** Boot backs off: the bean is typed
`FilterRegistrationBean<ForwardedHeaderFilter>`, and the e2e test asserts that exactly one filter is registered.
It runs at `HIGHEST_PRECEDENCE`, before the session filter (MIN+50), Spring Security (−100) and `RealmRoutingFilter`
(`DEFAULT_FILTER_ORDER − 10`), and on the REQUEST, ASYNC and ERROR dispatcher types. For an untrusted peer,
`removeOnly` hides every Spring forwarded header: `Forwarded`, `X-Forwarded-Host/-Port/-Proto/-Prefix/-Ssl/-For`.
The inner remover's already-filtered attribute name is different from the outer filter's, so it does run. The issuer
e2e test is genuine: it drives the real discovery endpoint, and it went RED (evil issuer) against plain Spring
behaviour; a control run with the list set to localhost turns RED again. Gaps: findings 5 and 6.

## Tests

The new tests are real and non-vacuous. Each had a documented RED run, and the reviewer re-ran the targeted classes
(all green). Existing assertions changed in two places:
- `RateLimitFilterTest.honoursXForwardedFor_forPerIpBudget` encoded the vulnerable behaviour. It was replaced by an
  untrusted-peer test (expects 429) and a trusted-proxy test. The XFF values in the trusted test were simplified; the
  old `"203.0.113.5, 10.0.0.1"` would still pass under the right-to-left walk, so this is not a weakening.
- In `FederationProviderFactoryTest`, two fixtures changed from non-ladder minimums (`urn:loa`, `…:Substantieel`) to
  `…:Substantial`. That is required by the fail-closed change, and `…:Substantieel` is now asserted to be rejected.

The local MFA e2e suites (`MfaE2eTest`, `MfaGateBrowserE2eTest`, `SamlMfaGateBrowserE2eTest`) are untouched.

Missing tests:
- a federated sign-in into a realm that **requires** MFA, for a user who is not enrolled (finding 1);
- `X-Forwarded-Ssl` alone from an untrusted peer (covered by Spring's header list, but not asserted);
- a `Host`-header issuer test (finding 6).
